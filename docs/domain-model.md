# MeetSpace — Domain Model

Версия: 1.0 | Статус: Проектирование

---

## 1. Общие соглашения

- Идентификаторы: `Guid`, генерируются на стороне приложения.
- Named constants: магические числа заменены именованными константами.
- Валидация бизнес-правил — на уровне Application/Domain, а не только в БД.
- Хранение даты/времени: `DateTime` с `DateTimeKind.Unspecified` (без временной зоны), как требует goal.md п. 4.

---

## 2. Представление ролей

```csharp
// Namespace: MeetSpace.Domain.Enums
public enum UserRole
{
    User = 1,
    Manager = 2
}
```

- Обычное перечисление (enum), а не отдельная сущность.
- Причина: роли фиксированы бизнес-требованиями (User, Manager), не требуется динамическое добавление.

## 3. Сущности

### 3.1. User

**Назначение:** учётная запись пользователя системы.

#### Поля

| Поле | Тип C# | Обязательное | Ограничения | Примечание |
|---|---|---|---|---|
| `Id` | `Guid` | Да | PK | Генерируется при создании |
| `FirstName` | `string` | Да | `[1..100]` символов, не пустая | |
| `LastName` | `string` | Да | `[1..100]` символов, не пустая | |
| `Email` | `string` | Да | `[1..255]`, RFC-подобный email, уникальный в БД | Используется для входа |
| `PasswordHash` | `string` | Да | BCrypt-хеш (60 символов) | Пароль в открытом виде не хранится |
| `ProfilePhotoKey` | `string?` | Нет | `null` либо S3-ключ | Хранится ключ объекта в S3/MinIO |
| `Role` | `UserRole` | Да | `UserRole.User` или `UserRole.Manager` | По умолчанию `UserRole.User` |

#### Связи

| Связь | Тип | Описание |
|---|---|---|
| `→ Booking` | One-to-Many | Пользователь может иметь много бронирований |
| `→ RefreshToken` | One-to-Many | Один пользователь — несколько refresh-токенов (логины с разных устройств) |

#### Ограничения и правила

- Email приводится к нижнему регистру при сохранении.
- `PasswordHash` формируется только через BCrypt (work factor ≥ 12).
- `ProfilePhotoKey` — путь к объекту в бакете `meet-space`, например `users/{userId}/avatar.jpg`.
- Роль нового пользователя всегда `User` при регистрации. Менеджер создаётся сидом.

### 3.2. Equipment

**Назначение:** справочник типов оборудования, доступного в комнатах.

#### Поля

| Поле | Тип C# | Обязательное | Ограничения | Примечание |
|---|---|---|---|---|
| `Id` | `Guid` | Да | PK | |
| `Name` | `string` | Да | `[1..50]` символов, уникальный | Например: «Проектор», «Доска» |

#### Связи

| Связь | Тип | Описание |
|---|---|---|
| `→ Room` | Many-to-Many | Через `RoomEquipment` |

#### Стартовый набор (сид)

1. Проектор
2. Доска
3. Телевизор
4. ВКС
5. Wi-Fi
6. Кондиционер

---

### 3.3. RoomEquipment

**Назначение:** промежуточная таблица для связи Many-to-Many между Room и Equipment.

#### Поля

| Поле | Тип C# | Обязательное | Ограничения | Примечание |
|---|---|---|---|---|
| `RoomId` | `Guid` | Да | FK → Room, часть составного PK | |
| `EquipmentId` | `Guid` | Да | FK → Equipment, часть составного PK | |

#### Связи

| Связь | Тип | Описание |
|---|---|---|
| `→ Room` | Many-to-One | |
| `→ Equipment` | Many-to-One | |

#### Ограничения

- Составной первичный ключ `(RoomId, EquipmentId)`.
- Пара уникальна — комната не может иметь один тип оборудования дважды.

> **Решение:** явная промежуточная сущность, а не автоматическая EF-таблица, для ясности модели и возможности будущих метаданных (например, количество единиц оборудования).

---

### 3.4. Room

**Назначение:** переговорная комната, которую можно бронировать.

#### Поля

| Поле | Тип C# | Обязательное | Ограничения | Примечание |
|---|---|---|---|---|
| `Id` | `Guid` | Да | PK | |
| `Name` | `string` | Да | `[1..200]`, уникальный | Название комнаты |
| `Capacity` | `int` | Да | `≥ 1` | Максимальная вместимость |
| `Floor` | `int` | Да | `≥ 1` | Этаж |
| `Description` | `string?` | Нет | `[0..2000]` | Описание, опционально |
| `PhotoKey` | `string?` | Нет | `null` либо S3-ключ | `rooms/{roomId}/photo.jpg` |

#### Связи

| Связь | Тип | Описание |
|---|---|---|
| `→ Equipment` | Many-to-Many | Через `RoomEquipment` |
| `→ Booking` | One-to-Many | Комната используется во многих бронированиях |

#### Ограничения

- Уникальность `Name` — бизнес-правило (проверяется в Application-слое).
- `PhotoKey` — управляется только менеджером.

### 3.5. Booking

**Назначение:** бронирование комнаты пользователем на определённый интервал.

#### Поля

| Поле | Тип C# | Обязательное | Ограничения | Примечание |
|---|---|---|---|---|
| `Id` | `Guid` | Да | PK | |
| `Title` | `string` | Да | `[1..200]` | Название бронирования |
| `Description` | `string?` | Нет | `[0..2000]` | |
| `UserId` | `Guid` | Да | FK → User | Кто забронировал |
| `RoomId` | `Guid` | Да | FK → Room | Какую комнату |
| `Date` | `DateTime` | Да | Только дата (время = 00:00:00), `DateTimeKind.Unspecified` | День бронирования |
| `StartTime` | `TimeSpan` | Да | `09:00 ≤ value < 18:00`, минутная часть кратна 15 | Время начала |
| `EndTime` | `TimeSpan` | Да | `09:00 < value ≤ 18:00`, `EndTime > StartTime`, минутная часть кратна 15 | Время окончания |

#### Связи

| Связь | Тип | Описание |
|---|---|---|
| `User` | Many-to-One | Навигационное свойство |
| `Room` | Many-to-One | Навигационное свойство |

#### Представление даты и времени

- **Дата:** `DateTime Date` — хранит только календарную дату без времени и часового пояса. Значение `Kind = Unspecified`.
- **Время:** `TimeSpan StartTime`, `TimeSpan EndTime` — раздельное хранение даты и времени исключает проблемы с DateTime, содержащим и дату и время.
  > **Альтернатива рассмотрена, но отклонена:** хранение `DateTime Start` + `DateTime End` компактнее, но разделение Date + TimeSpan точнее отражает бизнес-модель (день бронирования + временной слот) и упрощает проверки пересечений.

#### Правила валидации (Domain / Application)

| Правило | Где проверяется | Комментарий |
|---|---|---|
| Бронь только в рабочее время (09:00–18:00) | Domain / Application | Константы `WorkingHoursStart`, `WorkingHoursEnd` |
| `EndTime > StartTime` | Domain | Инвариант сущности |
| Нельзя бронировать в прошлом (`Date >= today`) | Application | Требует знания текущей даты |
| Комната не занята в пересекающемся интервале | Application / DataAccess | Запрос к БД; при редактировании текущая бронь исключается из проверки |
| Минутная часть кратна 15 | Domain | Инвариант сущности |

#### Проверка занятости

Проверка занятости — на уровне **Application** (бизнес-логика) с поддержкой **DataAccess** (запрос пересечений).  
Алгоритм: две брони пересекаются, если `(RoomId совпадает) AND (Date совпадает) AND (StartTime < other.EndTime) AND (EndTime > other.StartTime)`.

### 3.6. RefreshToken

**Назначение:** токен для обновления JWT access-токена.

#### Поля

| Поле | Тип C# | Обязательное | Ограничения | Примечание |
|---|---|---|---|---|
| `Id` | `Guid` | Да | PK | |
| `Token` | `string` | Да | Криптостойкая случайная строка, уникальная | Сам refresh-токен |
| `UserId` | `Guid` | Да | FK → User | |
| `ExpiresAt` | `DateTime` | Да | `DateTimeKind.Utc` | Срок действия — 14 дней от выдачи |
| `CreatedAt` | `DateTime` | Да | `DateTimeKind.Utc` | Момент создания |

#### Связи

| Связь | Тип | Описание |
|---|---|---|
| `User` | Many-to-One | Навигационное свойство |

#### Правила жизненного цикла

- Создаётся при успешном логине.
- Срок действия — 14 дней от `CreatedAt`.
- При использовании: старый refresh-токен **инвалидируется и заменяется новым** (ротация).
- При logout: все refresh-токены пользователя удаляются.
- Просроченные токены удаляются фоновой очисткой (или при login).
